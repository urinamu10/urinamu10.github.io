## 1. 노션 데이터베이스로 하루 일정을 관리하기

내가 노션에서 관리하고있는 아키텍쳐 구조를 어떻게 하면 더 잘 사용할 수 있는지 고민해보기 시작했다.

이 역시도 데이터 엔지니어링과 밀접한 공부가 된다는것을 알게되었기 때문이기도하고 사실상 데이터 ERD 구조를 어떻게 설계해야하는지 그대로 학습 할 수 있는 기회였기 때문이다.

내가 만든 노션의 OS 구조에서는 유명한 워크플로우 방식인 티아고 포르테의 PARA 4분류를 사용하는데, 영역(Area), 자원(Resource), 프로젝트(Project),  아카이브 (Archives)를 사용했다.

내가 머물고 있는 모든 장기적인 영역을 `Area DB`로 분류하고 그 속에서 이루고 싶은 목표를 `Goal DB`이라는 데이터베이스로 분류한다
그리고 그 목표를 이루기 위한 하위 프로젝트들을 `project DB`에 정리시키고 해당 프로젝트를 이루기 위한 하위집합인 `Tasks DB`로 분류해서 내 인생 전체를 관리하는 시스템을 만드는것이 최종적인 목표였다

> Area → Goal → Project → tasks → Archive
> 

각각 별개의 데이터베이스로 구성되어있으면서 동시에 관계형 속성으로 묶여 있는 구조이다.

### 1-1 노션의 특이한 구조

![alt text](/assets/img/image1111.png)

그런데 노션은 블록 위에 블록을 쌓는 형식의 구조를 가지고있다
즉, 데이터로 치면 표안에 표를 넣는 형식이다 이걸 page라고 칭하는데 표안에 행들이 각각의 page 구조로 끝없이 이어지는 구조라 한 분야 내에서 심화된 지점까지 기록해둘 수가 있는점이 장점이다
또 내가 사용중인 것은 상단의 여러 데이터베이스들을 제외하고 daily blog라는 DB도 별개로 운영중인데 그곳엔 오늘 내가 배운 것들을 총 정리하는 TIL(Till i learned)같은 곳이라고 생각한다.
부트캠프를 수료하기전엔 단순히 오늘 기분이 어땠는지, 어제보다 발전한 부분은 뭐고 배운것은 뭔지, 오늘 하루에 집중했는지 등등 간단하게 기록하고 속성(컬럼)을 통해 손쉽게 확인할 수 있도록 해두었는데
어느순간부터 Github 블로그에 매일 내용을 올리는것보다 차라리 daily Blog DB에 매일 기록하고 토요일에 내용을 종합, 정제해서 일주일에 단 한번만 업로드 시키는 방향이 낫다는 판단이 들었다.


근데 이 부분에서 여러가지 혼동이 오기 시작했다.
예를들어서 

![alt text](/assets/img/image1113.png)

제미나이에게 부탁해 만든 `커리큘럼 DB`라는게 있는데 내가 데이터 엔지니어로 취업하기 위해서 총 5개월의 로드맵을 csv로 받아 그대로 노션에 이식한 DB이다.

> 그럼 내가 그날에 배운 내용을 이 커리큘럼 DB 페이지 안에 기록해두면 되는건가?
> 

외부 DB가 하나 생기면 기존에 `daily Blog DB`와 연결시키는건 그리 어렵지 않다
관계형 속성을 하나 만들어서 `커리큘럼 DB ↔ Daily Blog DB`  두개를 연결시키면 되기 때문이다.
이건 SQL이나 Python의 join과도 같다 공통 컬럼을 통해 양측을 유연하게 연결시키면 되니까

하지만 만약에 여러 프로젝트들이 쌓이고 쌓이다가 외부 DB가 너무 많아지면? 
각 프로젝트나 목표마다 독립적인 DB가 존재하고 그걸 매번 연결시켜야한다면 언젠간 관리해야할 DB들이 너무 많이질 가능성이 생기게되고 
이 부분을 엔지니어가 가장 경계해야할 상황이라고 배울 수 있었다.

유지보수 비용이 늘고 데이터의 정합성과 무결성이 훼손될 수 있기때문이다
엔지니어는 분석가나 이해관계자에게 원하는 데이터를 최소한의 비용과 리소스 그리고 속도로 전달해줘야하는데 복잡한 스키마는 이를 방해할 가능성이 생긴다.

### 1-2 그럼 수동으로 시스템에 이식해야할까?

더 좋은 방식은 내가 이미 만들어둔 `Area`부터 `Archive`의 구조에 외부DB를 직접 이식해서 한개의 시스템과 그 안에 속한 DB 구조에 녹여내는것이 중요하다.

DB에 기록한다는건 미래의 내가 더 빨리 찾을 수 있고 한눈에 식별할 수 있도록 설계하는 것이고 
비단, 개인적인 시스템이 아니더라도 실무적으로도 융통되는 상황일것이다 (물론 실제 실무에선 더 좋은 방식을 쓸 수 있을지도!!)

![alt text](/assets/img/favicons/image1114.png)

결국 커리큘럼 DB라는 외부 데이터를 `Project`와 `Tasks`에 직접 이식했고 기존에 사용하던 시스템에서 그대로 사용할 수 있게되었다

그리고 `Daily Blog DB` 와 관계형 속성으로 묶어 각 커리큘럼의 행을 매일 작성시킨 블로그와 연결시키게 되었다.

이런 구조의 방식이라면 `Project DB` 내에서 해당 주차에 어떤 공부를 했었고 무슨 오류를 만나 해결했는지 한눈에 볼 수 있을뿐만 아니라
`Daily DB` 측에서도 빠르게 집계할 수 있을것이다.

정말 짧은 시간에 각 테이블간의 구조와 ERD, 스키마 설계방식 그리고 효율성에 대해 심화된 생각을 해볼 수 있었다.
물론 저 방식이 최적의 방식은 아닐것이다 더 좋은 파이프라인을 설계하는 방식이 분명히 있을것이고 그 과정을 배우는 중에 있다.
또한 노션에서 사용중인 OS 구조에 대해서도 꾸준히 발전시켜 나와 기업이 원하는 형태의 데이터베이스를 개발하고 관리하는 방식을 배우고싶다.

## 2. IBM 데이터 엔지니어링 1챕터 

![alt text](/assets/img/favicons/image1115.png)


본격적으로 데이터 엔지니어링에 대해 공부하기 시작했다.

내가 기초를 잡기 위해 선택한 강의는 Coursera의 IBM 데이터 엔지니어 전문 과정이다.
해당 강의에선 데이터 엔지니어가 무슨 역할을 하고 엔지니어링에 무슨 롤(역할)이 있으며, 누구와 협업하는지에 대한 내용이 초반부 목차에 배치되어있었다.

위 이미지 내용처럼 총 4가지의 대표적인 룰이 있으며 각각 수행하는 역할이 다르다는 부분을 설명했다.

1. Data warehouse engineer 
    
    데이터 웨어하우스 엔지니어는 가장 먼저 **“데이터 엔지니어”** 라고 생각했을때 떠오르는 역할로써 데이터 파이프라인과 웨어하우스에 집중하는 역할이다.
    
    ETL / ELT 파이프라인, 데이터 변환 및 웨어하우스 관리에 대한 역할을 맡는다.
    
    주로 사용하는 도구는 Apache Kafak, Spark, Cloud data warehouses
    
2. Data Architect 
    
    데이터 아키텍트는 이러한 데이터 웨어하우스를 설계하고 빅데이터 시스템을 설계하며, 분석 플랫폼을 개발하는 역할이다.
    
    이 역시도 내가 생각한 엔지니어의 역할과 가장 맞닿아있는 룰로
    
    주로 사용하는 도구는 ERD tools와 MYSQL, MongoDB, Cloud data Platforms  
    
3. Data Manager
    
    데이터 매니저는 데이터 거버넌스와 규정을 관리하며 이를 벗어나지 않도록 항상 감시하는 역할을 맡는다.
    
    일종의 법무관처럼 데이터가 법과 규정에 어긋나지 않도록 조율하는 역할이다
    
4. Database administrator
    
    데이터 관리자는 엔지니어 및 설계자와 협력하여 시스템의 안정성을 보장한다.
    또한 마지막으로 각 역할이 광범위한 데이터 생태계에 어떻게 기여하는지를 살펴본다.
    
    주로 사용하는 툴은 SQL과 Database 감시 모니터링 도구
    

위 4개의 대표적인 룰들은 서로 협력하여 데이터를 전반적으로 개발, 유지보수, 감시하며 기업에게 더 나은 의사결정 능력을 부여하는 역할로써 작동된다.

### 2-1 데이터 에코시스템과 데이터 엔지니어링의 역할
![alt text](/assets/img/image1116.png)
출처 - https://avplaybook.com/design-data-ecosystems-e4ac14a6cc50


현대의 데이터 에코 시스템은 상호 연결되고 독립적이며 지속적으로 진화하는 개체로 구성된 전체 네트워크가 포함된다.

지난 20년전엔 대부분의 데이터 엔지니어링잉 관계형 데이터베이스를 기반으로 수직적이고 느린 데이터 속도와 대역폭으로 의사결정을 도와주는 형식이였지만

새로운 도구와 끊임없는 발명 전 세계의 새로운 데이터 생성자와 소비자의 꾸준한 추가 속에서 데이터는 지속적인 선순환을 거쳐 더 많은 데이터를 낳게되는 상황이 되었다.

여기엔 통찰력을 창출하기 위한 다양한 유형의 분석 및 기술과 생선된 통찰력을 기반으로 협업하고 조치를 취하는 적극적인 이해관계자, 필요에 따라 데이터를 저장, 처리 및 배포하기 위한 도구, 애플리케이션 및 인프라가 포함된다.


### 2-2 데이터 파이프라인 순서

다양한 데이터 원본으로 작업할 때 가장 먼저 해야할 일은 원본의 데이터 사본을 데이터 레포지토리(저장소)로 가져오는것이다.

이 단계에선 데이터를 가져오는데 사용할 수 있는 데이터 형식, 소스 및 인터페이스를 사용하여 필요한 데이터를 확보하는 일만 남게되는데
수집되는 데이터의 신뢰성, 보안 및 무결성은 이 단계에서 해결해야하는 부분들

> 원시데이터 - > 저장소

또한 공통 위치에 원시데이터를 배치한 이후엔 사용자가 액세스 할 수 있도록 구성, 정리 및 최적화해야한다.

예를들어, IoT 장치일 경우엔 건강이나 생체 인식 또는 가정 데이터와 같은 개인 데이터의 저장 및 사용을 규제하는 지침을 준수하고, 조직의 모든 애플리케이션과 시스템에서 마스터 데이터를 표준화하기 위해 조직 내 마스터 테이블을 준수하는것도 또 다른 예가 될 수 있다.


### 2-3 데이터의 저장 기술 종류

현대엔 데이터 저장 및 분석 기술이 발전하면서 이를 합친 개념까지 등장하며 총 4개의 대표 유형으로 저장 방식을 나눌 수 가 있다.

#### 1. 데이터 웨어하우스 (Data Warehouse, DW)
![alt text](/assets/img/image1117.png)

- 특징: 정제된 정형 데이터를 저장하며, 특정 및 보고(BI)에 최적화 되어있음
- 용도: 빠르고 정확한 데이터 분석, 비즈니스 인텔리전스(BI)
- 구조: 구조화된 스키마(Schema-on-write)를 사용

#### 2. 데이터 레이크 (Data Lake, DL)
![alt text](/assets/img/image1118.png)

- 특징: 원시(Raw) 데이터를 정제없이 그대로 저장하며, 비정형/반정형 데이터를 포함한 대규모 데이터를 수용
- 용도: 머신러닝, AI 데이터 과학연구
- 구조: 데이터 읽기 시점에 스키마를 정의(Schema-on-read)

#### 3. 데이터 레이크 하우스 (Data Lakehouse)
![alt text](/assets/img/image1119.png)

- 특징: 데이터 레이크의 유연성(비용 효율)과 웨어하우스의 성능(ACID 트랜잭션, 데이터 무결성)을 결합한 최신 아키텍쳐
- 용도: 데이터 분석과 AI/ML을 하나의 통합 플랫폼에서 처리


#### 4. 데이터 마트 (Data Mart)
![alt text](/assets/img/image1120.png)

- 특징: 데이터 웨어하우스의 부분집합으로, 마케팅, 재무 등 특정 부서나 특정 목적에 맞춘 데이터 저장소
- 용도: 특정 부서의 신속한 데이터 분석


### 2-4 20년전과 현재 데이터 엔지니어링

지난 수십년 동안 데이터 엔지니어링이 어떻게 발전해 왔는지에 대해서 엔지니어는 공부할 필요성이 있다.

20년전과 지금을 비교하면 거의 알아볼 수 없는 수준이라고 말한다.
우리가 오늘날에 처리하는 엄청난 양의 데이터는 20년전엔 상상조차 할 수 없는 일이였고 현재는 다양한 형식의 데이터를 처리하는데 과거엔 존재조차 하지 않았던 종류의 데이터들이기때문이다.

또 최근엔 NOSQL(Not Only SQL) 데이터베이스처럼 수직 표가 아닌 키-값 또는 문서, 비정형 데이터들도 많은 기업과 조직에서 거의 안정적으로 사용되고 있다.

가장 중요한것은 자동화 도구를 사용하지 않고는 현대 데이터 엔지니어링 서비스를 실행할 수 없다는 것이다.

아마 차후 배울 Apache Airflow같은 오케스트라 스트리밍 서비스가 대표적일것이다.

최근 데이터 엔지니어들은 처음부터 해야할 일이 훨씬 적어적다고 말한다.

더 중요한 비즈니스 문제에 시간을 할애할 수 있고 이러한 시스템을 설정하고 관리하는데 드는 시간을 줄일 수 있다.

결국 핵심적인것은 다양한 빅데이터 시스템 및 파이프라인을 사용하는 방법을 터득해야할 필요성이 있다.
